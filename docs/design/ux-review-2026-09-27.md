# Build Mate UX review — 27 September 2026

Status: design recommendations, not an implementation specification. App source reviewed at `a2a3193`, alongside the user's Build Mate screenshots and two supplied Grok Bot screenshots. No application behavior was changed for this review.

## Assessment

Build Mate's core structure is sound: projects, conversations, tasks and a review step. Its visual weight comes from presenting too much of each task's machinery at once. Navigation, execution controls, model selection, a duplicated brief, a lifecycle checklist and detailed evidence compete with the conversation.

The strongest direction is subtraction and clearer placement. Keep the existing restrained light/dark appearance and native Mac controls. Make the conversation the main surface, with one truthful state and a clearly identifiable next action. Reveal supporting detail when it is useful.

The Grok Bot screenshots make that direction concrete:

- Bubbles fit their content instead of turning every short reply into a wide panel.
- Speaker identity is conveyed by alignment and appearance. Timestamps appear at useful intervals.
- The header contains little; settings occupy a separate panel.
- Empty space separates content without a box or divider around every item.
- The composer stays compact and predictable.

Borrow those principles, while retaining the status, repository access and review decisions that a coding workflow needs. The screenshots alone do not establish Grok Bot's behavior, accessibility or usability in other states.

## Highest-priority findings

### 1. Separate navigation from operating the agent

**Current:** Back, Forward and Inspector share an automatically placed toolbar group. The task view appends model/effort, editor, Delete and Pause. Their scopes are different but their presentation makes them look like one related control cluster.

**Recommendation:** Keep navigation leading and the inspector trailing. Keep one direct, icon-only editor shortcut separate from navigation. Move model/effort to the composer, task Pause/Resume beside task status, and Delete into the task's visible More menu. Keep Delete in card/row context menus and the menu bar. Project and global pause belong with their corresponding project/global context.

This follows Apple's guidance to group related actions, limit toolbar groups and retain menu-bar access to toolbar commands. Exact placement is our product decision. [Apple: Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)

Evidence: [MainWindow.swift](../../BuildMate/UI/MainWindow.swift), lines 88–109; [TaskDetailView.swift](../../BuildMate/UI/TaskDetailView.swift), lines 189–199.

### 2. Replace the checklist with an honest current state

**Current:** The five-step indicator is inferred from task state. Building highlights “Built”; In PR highlights “Merged”; clarification resets it to the beginning. It conveys false precision and uses a large part of the inspector.

**Recommendation:** One current-state label beneath the task title. Show a subordinate blocker or activity only when useful. A task's lifecycle stage and the agent's current operation are distinct. Keep history available through a disclosure instead of displaying every state change as a separate conversation row.

The proposed lifecycle vocabulary — Queued, Planning, Building, Testing, Waiting for Review, In PR, Merged — needs real state transitions before those labels can be reliable. Keep Needs Clarification as an attention condition associated with a stage. Do not manufacture Planning/Testing from tool activity or elapsed time as part of a cosmetic redesign.

Evidence: [Components.swift](../../BuildMate/UI/Components.swift), lines 31–52.

### 3. Give the conversation room

**Current:** A large brief precedes the transcript and repeats in the inspector. Each bubble contains author and time. Inner maximum-width frames stretch short messages. The inspector starts open, narrowing the chat even when there is nothing to review.

**Recommendation:** Keep one editable Brief disclosure, open initially for an unstarted task and otherwise remembered. Let message bubbles size to content with a readable maximum width. Remove repeated visible “You” and “Agent”; preserve those labels for accessibility. Use time separators for meaningful gaps, and expose exact timestamps on focus/context action. Default to the conversation with details closed on first use, then remember the user's choice. Never reopen the inspector automatically over their work.

Keep a visible Review action when evidence is ready so review does not depend on discovering the inspector. Pending plan approval also needs its plan and Approve Plan action in the main surface; these currently live in the inspector. Reuse block Markdown rendering for agent replies and plans, including lists and code, rather than leaving it limited to briefs and proof reports.

Evidence: [TaskDetailView.swift](../../BuildMate/UI/TaskDetailView.swift), lines 34–66 and 117–123; [AppModel.swift](../../BuildMate/UI/AppModel.swift), line 70; [ChatTranscript.swift](../../BuildMate/UI/ChatTranscript.swift).

### 4. Fix scrolling and drafting before adding more animation

**Current:** Task chat has no explicit follow-latest behavior. Project chat scrolls to the bottom on new messages while busy, even if the user is reading earlier content. Its text field is disabled during a response, preventing the next message from being drafted. Unsent task text is local view state and is lost when navigating away; project chat already keeps its draft outside the view.

**Recommendation:** Use the same behavior in both chats: follow new output only while already near the bottom; preserve position when reading history; provide a quiet “Latest” action when new content arrives offscreen. Preserve unsent drafts when switching tasks. Allow drafting during a response. Any next-message queue or steering behavior must be explicit; do not silently discard or submit a draft.

Keep the existing typing-to-message morph and Reduce Motion support. Streaming should not make the viewport bounce.

Evidence: [TaskDetailView.swift](../../BuildMate/UI/TaskDetailView.swift), line 32; [ProjectChatView.swift](../../BuildMate/UI/ProjectChatView.swift), lines 56–70.

### 5. Make “Needs You” mean a human decision is required

**Current:** Scheduled automatic retries are counted as attention items and can generate a notification on each attempt. Review previews still insert raw `proof.summary` or the full plan into plain text, so JSON and Markdown syntax can leak into this screen despite the repaired proof viewer.

**Recommendation:** Show task title, project and the decision needed. Use a brief readable summary and open the task for evidence. Quietly show “Retrying…” where work is happening; notify for exhausted recovery or a genuine decision. An error should explain what the person can do, with diagnostic text behind disclosure. Clear it when resolved.

Evidence: [AppModel.swift](../../BuildMate/UI/AppModel.swift), lines 137–167; [NeedsYouView.swift](../../BuildMate/UI/NeedsYouView.swift), lines 45–75; [AttentionNotifications.swift](../../BuildMate/UI/AttentionNotifications.swift).

### 6. Remove controls that fail in their current context

**Current:** “Search tasks” is attached to the whole main window, but only task collections and parts of Needs You consume it. It has no visible effect in conversations, task detail or Instructions. Project Pause is attached to the board branch and disappears in list view. List rows also omit useful paused/retry/dependency notices and some card actions.

**Recommendation:** Scope search to searchable collections, preserve it per context and use “No matches” for an empty search result. Keep project Pause/Resume and task exception information consistent in board and list. Do not restore redundant normal state labels on cards already grouped by state.

Evidence: [MainWindow.swift](../../BuildMate/UI/MainWindow.swift), line 109; [TaskBoard.swift](../../BuildMate/UI/TaskBoard.swift), lines 50–86; [AppModel.swift](../../BuildMate/UI/AppModel.swift), task filtering.

## Where controls should live

| Scope | Visible by default | Disclosed or secondary |
|---|---|---|
| Window navigation | Back/Forward leading; details toggle trailing | Native View menu and shortcuts |
| Global work | Compact activity/usage in the sidebar footer; accessible Pause All | Usage windows, reset dates, refresh and override in the existing popover |
| Project | Project identity, Chat/Tasks navigation; visible paused state and Resume when relevant | Project menu: Pause, Instructions, settings and location actions |
| Task | Title, current state; Pause/Resume while applicable; one direct editor icon | More: Edit task, Delete; details: worktree, Terminal, Finder and history |
| Conversation | Attach, Screenshot, input, Send/Stop response; compact model/effort | Attachment previews and removal only when attachments exist |
| Review | Short change summary, evidence access, one primary review action | Passed checks, logs, proof options and preview configuration |

Do not conflate Stop response with Pause task or Pause All. A native More menu is a discoverable home for occasional actions; right-click is an additional route, never their only route.

## Screen-specific refinements

### Sidebar and Tasks

- Remember project expansion. Avoid expanding every project's Chat/Tasks/Instructions rows by default. Move Instructions to a clearly named project menu, keeping keyboard access.
- Reduce the footer to compact activity and usage. Expand consequential exceptions such as a usage hold. Preserve the stale-data indication and ensure VoiceOver announces holds and stale data, not only a percentage.
- Use one obvious New Task action in the Tasks context, retaining Command-N throughout the app. Do not put the same creation control in both the toolbar and Queue header.
- Six board columns currently need roughly 1,330 points before the sidebar is counted. At the window's 1,100-point minimum, later columns require horizontal scrolling. Keep readable card widths and Merged access; make scrolling clear and the list alternative easy to reach. Do not squeeze columns or shrink text to pretend everything fits.
- Remove repeated “No tasks” text in every empty column. One helpful empty-board state is enough. Keep state icons, counts and meaningful paused/blocked indicators.
- Treat drag-and-drop as moving an object: stable pickup size, a clear insertion gap, restrained sibling movement and no content flashing. Verify this interactively; source review alone cannot establish smoothness. Preserve keyboard/menu alternatives.

Evidence: [MainWindow.swift](../../BuildMate/UI/MainWindow.swift), [TaskBoard.swift](../../BuildMate/UI/TaskBoard.swift), [UsageFooter.swift](../../BuildMate/UI/UsageFooter.swift).

### Project chat

- Make the header and composer match task chat, with the model/effort control in the same place.
- Keep recent created tasks newest first; show a compact recent set with View All instead of an indefinitely growing wall of divided rows. Five is a reasonable initial presentation limit, subject to testing.
- Keep Project information pinned at the inspector bottom as requested. Show the project name and concise location; disclose branch/remote details. Remove the paragraph explaining separate agent checkouts and the duplicate Open Tasks shortcut.
- Use the actual waiting reason. The current queued label can claim “Waiting for an agent slot” while account usage is the constraint.

Evidence: [ProjectChatView.swift](../../BuildMate/UI/ProjectChatView.swift), lines 44–46 and 87–137.

### Review

- Order the content: what changed, inspect changes/evidence, checks, decision. Keep the primary Open/Update Pull Request action reachable without scrolling through diagnostics.
- Collapse passed checks into a concise disclosure; expand failures. Omit “Recording not required.” Put preview configuration with the preview action.
- Keep screenshot expansion/Open in Preview and recording playback. These are valuable inspection tools the user explicitly requested.
- Keep review summaries readable and PR descriptions limited to the change summary. The recent JSON-to-Markdown fixes are useful; finish applying them to all entry points.

Evidence: [LifecycleViews.swift](../../BuildMate/UI/LifecycleViews.swift), `ReviewEvidence` and `PreviewControls`; [TaskDetailView.swift](../../BuildMate/UI/TaskDetailView.swift), inspector.

### New Task, project setup and Settings

- New Task should initially show project, brief, attachments, Cancel and Add to queue. Put optional title, proof override and plan approval under Options, inheriting project defaults.
- Delete the permanent title-generation explanation and repeated queue instructions. Show a dispatch explanation only for a real blocker, such as a paused project.
- Keep Agents at once. Remove Heavy steps from normal Settings and manage proof/preview capacity internally. The current term is ambiguous and exposes scheduling implementation.
- Remove the ordinary user-facing turn budget. The default 20-turn ceiling currently applies to a persisted session count, despite the tooltip claiming “per task attempt”; routine revisions can eventually hit it. Replace that maintenance burden with deliberate internal stall/runaway handling rather than merely hiding an unexplained stop.
- Keep technical timeout/backoff controls in diagnostics if support needs them, expressed in human units. Do not remove network/security controls as visual cleanup.
- Keep the chosen default editor, plan-approval preference and notification settings. Do not add new appearance/density preferences for decisions we can make well by default.
- Folder selection already inspects the repository; avoid presenting Check Repository as a mandatory second step on that path. Keep rechecking available when a path or authentication problem changes.

Apple recommends minimizing settings and choosing defaults that work for most people. [Apple: Settings](https://developer.apple.com/design/human-interface-guidelines/settings)

Evidence: [ProjectSheets.swift](../../BuildMate/UI/ProjectSheets.swift), lines 198–230; [SettingsView.swift](../../BuildMate/UI/SettingsView.swift), lines 10–39; [Orchestrator.swift](../../BuildMate/Core/Orchestrator.swift), lines 504–515.

## Remove, retain and refine

**Remove from the normal presentation:** duplicate brief; misleading milestone checklist; per-bubble author labels; routine “saved/sent” explanations; repeated empty-column messages; checkout implementation tutorial; “Recording not required”; promotional “Build with a little help”; unnecessary New Task explanation paragraphs.

**Move or collapse:** toolbar trash, model/effort, detailed usage, successful check logs, full paths, Instructions, preview configuration, old created-task lists and routine state-change history.

**Retain:** explicit task state, useful blockers, model/effort editable at any time, attachments and screenshots, icon-only editor access, Terminal/Finder, task deletion from detail and context menus, review evidence, Merged, tooltips, keyboard commands and pause controls with clear scopes.

Several questionable controls, including turn limits and heavy-step limits, came from the written specification. They should not be described as proven unsolicited inventions. Their utility and presentation still deserve revision, particularly after the user questioned them.

## Visual craft and Mac behavior

Use standard toolbar placement, native menus, SF Symbols, system text styles and accessible colors. Keep surfaces calm and avoid adding more badges, gradients, border treatments or cards. Use spacing and typography to establish hierarchy; keep dense technical text in disclosures. Reserve glass for functional navigation and controls rather than spreading it through content. [Apple: Materials](https://developer.apple.com/design/human-interface-guidelines/materials)

Make icon hit areas and optical alignment consistent, particularly in the composer. Align short and multiline input to the same stable control row. Keep tooltip labels specific about scope: “Pause task,” “Pause project,” “Pause all work.” Do not make essential commands hover-only.

Animation should explain change: picking up a card, inserting it between others, expanding details and the typing bubble becoming a response. Avoid ambient movement, repeated whole-transcript animation and competing loading indicators. Preserve Reduce Motion and do not use motion as the only state signal.

Use an optional native inspector for supporting context. Keep urgent questions, pending plan approval and review availability in the main task surface when it is closed. At narrower widths, allow panes to collapse; do not make all content smaller.

## Recommended delivery order

1. **Correctness and hierarchy:** truthful state, scoped search, consistent board/list actions, chat scrolling/drafting, clean attention summaries and quiet automatic retries.
2. **Subtraction and placement:** toolbar/composer changes, one brief, content-sized bubbles, simpler review, smaller sidebar/footer, New Task and Settings cleanup.
3. **Craft:** native light/dark verification, optical alignment, resizing, focus, keyboard/VoiceOver, drag/drop and Reduce Motion. Check long titles, code blocks, many attachments, empty projects, paused/usage-held work, clarification, review and In PR feedback.

Success means the user can immediately answer: what am I looking at, what is its real state, and is there anything I need to do? Supporting detail should remain easy to reach without dominating the screen.

The source and existing screenshots establish the findings above, but this is not a live pixel-level or accessibility sign-off. The proposed layout sketch illustrates hierarchy; native materials, menus, focus and motion still require verification in the app.

During implementation, reconcile stale specification sections: `01-product.md` still describes Backlog and the old checklist; `04-ux-mac.md` both excludes Merged from the board and later requires it. Follow the user's latest decisions and update those sections rather than reviving retired concepts.
